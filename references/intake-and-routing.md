# 需求摄取与动态路由契约

本文件定义 `$short-video-workflow` 如何根据用户需求的详细程度，决定先询问什么、
复用什么，以及调用哪些 Drama Skills。它只记录编排判断，不创建第二套剧本、资产或
提示词事实源。

## 目标

工作流入口是“先盘点，再按用户意图选择一次性补齐或阶段性执行”：

1. 读取用户请求、项目文件、已保存资产和当前 Canvas 状态。
2. 区分用户明确提出的内容、项目已有事实、可复用资产和真正缺失的信息。
3. 只询问会阻塞下一步或改变制作方案的关键条件。
4. 默认把所有缺口一次性编排到可生产状态；已有内容和可复用资产直接跳过。
5. 只有用户明确限定某个阶段时，才暂停在该阶段，不自动推进后续阶段。
6. 进入实际生产前，再展开该批次需要的完整制作包和确认闸口。

## 信息优先级

发生冲突时按以下顺序处理：

1. **本轮用户明确要求或明确修改**：优先级最高，允许覆盖项目中的旧创作决定或
   已保存资产的默认使用方式；覆盖必须记录为本轮意图。
2. **项目事实和已确认创作文档**：包括 `剧本.md`、`视觉设定.md`、`分镜.md`、
   `图片提示词.md`、`视频提示词.md` 以及项目规则文件。
3. **身份、风格、视角和状态都匹配的已保存资产**：直接复用，不重复生成。
4. **工作流默认值和创作推断**：只用于填充非阻塞项，并在设计报告中标明。

用户只说“使用现有角色/场景”时，应复用匹配资产；用户同时给出新的角色设想、
造型、关系或场景意图时，按用户意图建立变体或替换方案，不得静默沿用旧资产。

## 需求详细程度

将请求归入最接近的一类，不把分类本身展示为用户必须填写的表单：

| 类别 | 典型输入 | 处理方式 |
| --- | --- | --- |
| `brief` | “做一个武侠风短视频” | 先确认时长等阻塞合同条件，再一次性补齐缺失创作和生产准备 |
| `partial` | 有题材、人物或一句故事，但缺少部分制作信息 | 保留明确内容，一次性补齐其余必需阶段 |
| `detailed` | 有剧本、角色、场景或镜头要求，但缺少生产参数 | 读取项目事实，一次性补齐下游所需参数和未完成阶段 |
| `production_ready` | 剧本、参考资产、分镜、提示词和参数基本齐全 | 只做一致性检查、资产复用和生产确认，不重写创作内容 |
| `continuation` | “继续上次视频”“把上一版改成 9:16” | 从状态和批次恢复，只处理变更影响的阶段 |

详细程度不是质量评分，而是路由依据。它决定哪些内容可以直接复用、哪些阶段需要
补齐；默认执行范围仍是完整闭环。`brief` 不代表用户需要被追问所有创作细节；
`production_ready` 也不代表可以跳过状态、资产和参数校验。

## 执行范围

除非用户明确限定，`intake.executionScope` 使用 `end_to_end`：

- 用户说“帮我制作一个武侠风短视频”时，确认必要合同条件后，一次性完成故事、
  剧本、角色、场景、分镜、提示词、图片资产和视频确认前准备。
- 用户提供了剧本、角色或场景时，直接复用这些输入，并一次性补齐剩余缺口。
- 用户明确说“我们先做个剧情吧”“先只做角色设定”“先出分镜”，才使用
  `stage_only`，只执行该阶段及其不可避免的直接前置，不自动进入后续阶段。

`end_to_end` 的“一次性补齐”不等于可以虚构参考图或替用户选择文生视频。若角色、
场景或关键帧需要真实参考而当前没有可读文件/Canvas 图片，完成能完成的前期文档后，
保持视频交接为 `blocked`，一次列出缺口并等待“补图、PLAN 外部挂载或明确文生视频”
中的选择；不得静默跳过参考图。

`stage_only` 不是把完整流程拆成默认多轮确认，而是响应用户明确的阶段性创作意图。
用户后续说“继续做完整视频”时，重新盘点并把剩余阶段合并为一次完整闭环。

## 盘点维度

每次新请求至少盘点以下维度，并为每项标记 `explicit`、`project`、`reusable`、
`default` 或 `missing`：

- 交付目标：短视频、短剧、宣传片、游戏历程视频或其他视频形态。
- 制作合同：时长、集数、画幅、平台、声音/字幕、水印和输出格式。
- 故事：创意前提、冲突、结尾、剧本或故事方向。
- 角色：角色身份、关系、造型、角色设定图和可复用角色资产。
- 场景与道具：地点、空间关系、道具状态和可复用场景资产。
- 镜头：分镜、关键帧、节奏、动作和连续性要求。
- 提示词：图片提示词、视频提示词和参考图绑定。
- 生产：模型、尺寸、质量、时长、音频、成本边界和输出目标。
- 既有产物：当前项目文档、批次、媒体、Canvas 节点和用户上传素材。

盘点结果写入 `.short-drama/workflow-state.json` 的 `intake` 对象；创作内容仍必须
回写对应 Drama Markdown 文档。

## 询问规则

只提出当前阶段无法安全推断的阻塞问题，并按以下顺序处理：

1. **时长**：用户未给出时，默认先确认时长，因为它影响剧本密度、镜头数、视频
   任务数量和成本边界。用户明确授权工作流自行决定时，才可使用项目默认值。
2. **交付形态和画幅**：只有当多个形态或画幅会导致不同创作方案，且项目资料无法
   判断时才询问。
3. **内容边界或核心意图**：只有缺失会导致无法确定故事方向，或用户给出的参考
   彼此冲突时才询问。
4. **非阻塞偏好**：风格细节、配乐偏好、镜头数量等可以由对应 Skill 先提出
   合理方案，不要在入口一次性追问。

例如，“帮我制作一个武侠风短视频”至少先确认总时长；确认后可由 `$short-drama`
和对应 Drama Skills 一次性补齐剧情、角色、场景、分镜和提示词，不要求用户逐项填写
这些创作内容。只有用户说“我们先做个剧情吧”，才在剧情阶段结束后停下。

用户一次补充多个答案后，重新盘点并合并询问，避免重复询问已经得到的信息。若仍
有阻塞问题，状态为 `needs_user_input`；若没有阻塞问题，即使仍需创作，状态也应
为 `ready`，并进入路由。

## 缺口到 Skill 的路由

| 缺口或变更 | 默认责任 Skill | 行为 |
| --- | --- | --- |
| 项目初始化、跨阶段规划、故事开发决策 | `$short-drama` | 初始化或恢复项目，并建立创作阶段顺序 |
| 缺少故事方向、人物冲突或分集规划 | `$short-drama` | 先完成开发决策，再交给写作 |
| 有故事方向但缺少可拍剧本 | `$short-drama-write` | 只写缺少或需要修改的剧本部分 |
| 缺少角色、造型、场景、道具或连续性 | `$short-drama-assets` | 读取现有设定，新增或建立明确变体 |
| 缺少图片提示词 | `$short-drama-image-prompts` | 只为新增或变更资产/关键帧写提示词 |
| 缺少分镜或冻结关键帧 | `$short-drama-storyboard` | 基于当前剧本和视觉设定补镜头计划 |
| 缺少动作、表演或运镜提示词 | `$short-drama-video-prompts` | 基于已冻结镜头补视频提示词 |
| 已确认的图片、视频、配音或音乐实际生产 | `$short-drama-produce` | 仅在相应确认边界满足后执行 |
| 素材装配、字幕、响度和交付 | `$short-drama-edit` | 只处理交付阶段缺口 |
| 用户要求审查或路由闸门发现风险 | `$short-drama-review` | 只报告问题和修订要求，不代替责任 Skill |

阶段顺序仍由依赖关系决定，但默认路由是完整缺口闭环。例如已有剧本但缺角色设定
时，从 `$short-drama-assets` 开始并继续完成后续分镜、提示词和生产准备；已有全部
创作文档但缺视频提示词时，不重新开发故事，只补视频提示词及其生产准备。
只有 `stage_only` 请求才在指定阶段停止。

## 路由完成条件

进入下一个阶段前，`intake.route` 必须能回答：

- 本轮用户明确改变了什么？
- 哪些项目事实和资产将被复用？
- 哪些内容缺失或失效？
- 每个缺口由哪个 Skill 处理？
- 当前是否还有阻塞问题？
- 本轮是否允许进入图片生产或视频确认闸口？

不得因为一个缺口存在，就把所有其他阶段标记为缺失；也不得因为项目里有同名文件，
就假定其中内容与本轮请求匹配。
